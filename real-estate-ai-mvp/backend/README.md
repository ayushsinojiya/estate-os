# EstraOS API

Java 21 / Spring Boot 3.5, Spring Security JWT, PostgreSQL 17, Flyway, JPA identity records and tenant-scoped JDBC workflow repositories. Public API documentation is available at `/swagger-ui.html`; authorize with a login token and use the workspace ID returned by login.

## Run

Provide PostgreSQL and export the values documented in [.env.example](.env.example). Java/Maven does not automatically load `.env` files. `DATABASE_URL`, `DATABASE_USERNAME`, `DATABASE_PASSWORD`, and a random `JWT_SECRET` of at least 32 bytes are required.

```sh
mvn spring-boot:run
```

Flyway applies versioned schema migrations on startup; normal startup never deletes or resets data. All database IDs use `BIGINT GENERATED BY DEFAULT AS IDENTITY`; API identity fields are decimal strings to preserve JavaScript precision. The JPA identity uses `Long` and `@GeneratedValue(strategy = GenerationType.IDENTITY)`; JDBC insert statements omit `id` and retrieve `RETURNING id`.

For fictional demo data, set `SPRING_PROFILES_ACTIVE=demo`, `INTEGRATIONS_MODE=mock` and choose `DEMO_PASSWORD` with at least 12 characters. Sign in as `admin@estraos.demo`, `manager@estraos.demo`, or `agent@estraos.demo` using that supplied password. `agent2@estraos.demo` belongs only to the second demo workspace; the admin belongs to both. Demo initialization skips already seeded workspaces and never resets passwords. Do not enable the demo profile in production.

## Verify and package

```sh
mvn verify
mvn package
java -jar target/estraos-api-1.0.0.jar
```

Full integration tests start an isolated PostgreSQL 17 Testcontainer by default. When Docker is unavailable, provision a new empty disposable test database and export `TEST_DATABASE_URL`, `TEST_DATABASE_USERNAME`, and `TEST_DATABASE_PASSWORD`; the suite uses that database instead. These tests persist fictional data, so never point them at production. Each fresh test JVM generates its own demo password; use a fresh test database for each run. They validate migrations/identity IDs, authentication/logout, role/tenant isolation, lead validation, published content, recommendations, overlapping and concurrent bookings, cancellation, handover relationships, and notification ownership. Adapter and reminder tests use local mocks only. No live external provider is verified.

```sh
docker build -t estraos-backend .
docker run --rm -p 8080:8080 --env-file .env estraos-backend
```

Manage Docker networking and PostgreSQL separately. Inside a container, database and provider hostnames must be reachable from that container. Runtime image uses a non-root user. `/actuator/health` is public and contains no database details.

## Security and data design

### File storage

Set `FILE_STORAGE_PATH` to a directory writable by the service. File Management stores each
file under a generated workspace and file-ID directory, while PostgreSQL retains metadata and
soft-deletion history. Files are limited to 50 MB and support PDFs, Office documents, text,
Markdown, CSV, images, and ZIP archives. No download or public static-file API is provided.

Every business API checks a database-backed session and workspace membership. JWTs expire, logout revokes the stored session, and disabled accounts cannot continue using old tokens. Managers/admins manage inventory and content and view audit logs; agents manage customer workflows. Agent assignment requires an active real-estate-agent workspace member. Notifications are filtered to the current recipient. Related IDs are validated and composite workspace/project foreign keys reinforce ownership.

Write transactions use a workspace advisory lock for booking, availability-sensitive recommendations, unit updates and provider operations. This prevents overlapping agent/lead bookings through the API under concurrent requests. External service calls have bounded timeouts. Database administrator writes outside the API must preserve these invariants. Property and lead details live in JSONB beside normalized identity, ownership, status and indexed matching columns; support tables store append-only history snapshots. No RAG embeddings are stored here.

PDF registration stores metadata and an existing external storage reference. Original PDF bytes remain with the storage service; no PDF upload/parse engine is implemented. Demo storage references are labeled metadata-only and do not point to real files. Editable content is supplied manually or by your existing content pipeline. Editing published content unpublishes it through the RAG adapter before saving a draft. Retrieval includes only current published document IDs.

Use a stable `Idempotency-Key` header when starting an outbound call. The application caches successful starts by workspace/key; the same key with another lead is rejected. Providers must honor the forwarded request ID to cover unknown results after network timeouts. Real provider contracts, credentials, file bytes and delivery remain manual configuration; see [integration guide](../docs/integration.md).

Site-visit and callback reminders are persisted with due times, cancelled when rescheduled, and processed by a bounded scheduled worker. Provider deliveries are explicitly `MOCK_DELIVERED` in demo mode; this does not imply SMS/email delivery or customer confirmation. Failed/unknown provider outcomes remain visible and are not blindly retried.
